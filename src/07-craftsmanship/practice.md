# Code review, диагностика и перенос правил

Работайте с копией фрагмента. Сначала зафиксируйте прогноз и аргументы, только затем запускайте или изменяйте код. Готового решения здесь нет: результатом служат таблица наблюдений, patch и краткое обоснование со ссылками на конспекты.

## 1. Предсказать и объяснить управляющий поток

**Результат:** восстановить поведение функции и провести первый review по наблюдаемым фактам.

**Пререквизиты:** [[code-complete/3.vars/11.vars-naming|Именование переменных]], [[code-complete/4.operators/14.sequential-code-organization|организация последовательного кода]], [[code-complete/4.operators/15.if-operators|условные операторы]].

```typescript
type Order = {
  paid: boolean;
  address: string;
  blocked: boolean;
};

function shippingStatus(order: Order): string {
  let temp = "manual-review";

  if (order.paid) {
    if (order.address !== "") {
      if (!order.blocked) {
        temp = "ready";
      }
    }
  }

  return temp;
}
```

До запуска заполните таблицу для четырёх входов: оплаченный корректный заказ, неоплаченный заказ, заказ с пустым адресом и заблокированный заказ. Для каждого укажите пройденные условия и результат.

**Приёмка:**

- прогноз содержит четыре строки и конечное значение для каждой;
- запуск небольшого `console.log`-сценария совпадает с прогнозом;
- review содержит минимум три замечания: об имени или времени жизни переменной, о вложенности и о читаемости нормального пути;
- каждое замечание связано с конкретным правилом из пререквизитов, а не только с личным предпочтением.

**Контрольная точка:** отдельно проследите путь, на котором каждое из трёх условий впервые становится ложным; убедитесь, что функция всегда достигает одного `return`.

> [!hint]- Подсказка 1
> Начните с дерева из трёх вопросов. Не оценивайте следующий вопрос, если внешний `if` уже не выполнен.

> [!hint]- Подсказка 2
> Сравните имя `temp` с фактической ролью значения и посчитайте строки между его созданием и последним использованием.

**Рефлексия:** какое замечание снижает риск ошибки, а какое в основном уменьшает стоимость чтения? Как это различие повлияет на приоритет review-комментариев?

## 2. Модифицировать и диагностировать граничный случай

**Результат:** найти расхождение между контрактом и реализацией, затем упростить код без потери поведения.

**Пререквизиты:** выполненное задание 1; [[code-complete/4.operators/19.general-control-issues|позитивные выражения и глубокая вложенность]].

Контракт уточнён: статус `ready` допустим только для оплаченного, незаблокированного заказа с адресом, содержащим хотя бы один непробельный символ. Диагностируйте поведение исходной функции для адреса `"   "`, а затем измените её.

**Приёмка:**

- записаны ожидаемый и фактический результаты для пробельного адреса и названа проверка, из-за которой они расходятся;
- четыре исходных сценария из задания 1 сохраняют результаты;
- добавленный сценарий с `"   "` получает `manual-review`;
- нормальный путь читается без трёх уровней вложенности;
- проверка выполняется повторным запуском одной таблицы сценариев до и после изменения.

**Контрольная точка:** до рефакторинга добавьте падающий сценарий для пробельного адреса; после изменения он должен пройти вместе с исходными четырьмя.

> [!hint]- Подсказка 1
> Проверка `address !== ""` различает только пустую и непустую строки. Сначала сформулируйте, какое значение должно остаться после удаления пробельных символов.

> [!hint]- Подсказка 2
> Отделите причины ручной проверки от нормального хода. Ранний выход или одно составное условие могут убрать уровни, но выбранную форму нужно обосновать читаемостью.

**Рефлексия:** какой артефакт лучше защитил контракт — форма кода или таблица сценариев? Что случится, если появится ещё одна причина `manual-review`?

## 3. Реализовать и перенести правило в таблицу решений

**Результат:** перенести приёмы review на новую предметную область и реализовать приоритетные бизнес-правила как данные.

**Пререквизиты:** [[code-complete/4.operators/18.table-methods|Табличные методы]], [[code-complete/4.operators/19.general-control-issues|таблицы решений]].

Реализуйте на TypeScript функцию `accessDecision(context, rules)`, которая применяет первое совпавшее правило. Правила должны хранить условие и результат отдельно от универсального обхода.

| `blocked` | `role` | `paid` | Результат |
|---|---|---|---|
| `true` | любой | любой | `deny` |
| `false` | `admin` | любой | `allow` |
| `false` | `member` | `true` | `allow` |
| `false` | прочее | любой | `review` |

**Приёмка:**

- реализация покрывает все четыре строки таблицы и возвращает строку, а не печатает её внутри обработчика;
- блокировка имеет приоритет даже для оплаченного `admin`;
- порядок правил объявлен явно и проверен сценарием, где совпадают более одного общего условия;
- есть минимум по одному запускаемому сценарию на каждый результат и отдельный сценарий на приоритет;
- в review собственного решения отмечены связность обработчика, имена правил и место добавления нового результата.

**Контрольная точка:** сначала выполните условия правил вручную для заблокированного `admin`, затем сравните с результатом программы; после этого поменяйте местами два правила и объясните наблюдаемое изменение, не оставляя неверный порядок в итоговом варианте.

> [!hint]- Подсказка 1
> Представьте правило объектом с двумя полями: предикатом над контекстом и возвращаемым значением.

> [!hint]- Подсказка 2
> Универсальному обработчику достаточно найти первое совпадение. Самое специфичное и безопасное правило должно встретиться раньше общего.

**Рефлексия:** при каком росте числа условий таблица станет понятнее цепочки `if`, а при каком — сложнее? Назовите сигнал, после которого правила стоит разделить на несколько наборов.
