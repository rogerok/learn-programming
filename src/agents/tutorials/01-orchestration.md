# Оркестрация: coordinator–workers–verifier

## Базовая схема

```text
задача
  → сильная модель фиксирует цель и инварианты
  → дешёвые scouts/librarians параллельно локализуют контекст
  → сильная модель синтезирует факты и фиксирует общий контракт
  → дешёвые workers параллельно выполняют независимые срезы
  → reviewers проверяют отдельные риски
  → сильная модель интегрирует и выполняет end-to-end verification
```

Это две разные разновидности fan-out:

1. **исследовательский fan-out** — разрешён до архитектурного решения;
2. **исполнительский fan-out** — разрешён только после фиксации общего контракта.

## Ответственность основной модели

Нельзя делегировать:

- толкование пользовательского запроса;
- верхнеуровневую декомпозицию;
- общий API, schema и invariants;
- решение конфликтов между подсистемами;
- принятие неподтверждённых security или correctness выводов;
- интеграцию;
- финальную поведенческую проверку.

Субагенты не наследуют историю разговора автоматически. Каждое назначение должно содержать все требования своего среза: цель, ограничения, контракт, пути, non-goals и acceptance criteria.

## Как найти независимые срезы

Хорошие границы:

- разные подсистемы с уже существующим интерфейсом;
- разные платформы;
- разные гипотезы причины бага;
- разные библиотеки-кандидаты;
- независимые группы call sites после фиксации нового API;
- разные risk lenses одного review.

Плохие границы:

- «первые 20 файлов / следующие 20 файлов»;
- frontend и backend до определения общего payload;
- миграция consumer до появления нового provider API;
- несколько workers, меняющих один shared type;
- деление, при котором каждый агент вынужден читать один и тот же глобальный state.

Проверка независимости:

```text
Может ли срез B корректно завершиться, не увидев незавершённый результат A?
```

Если нет — сначала выполнить A или зафиксировать маленький общий контракт основной моделью.

## Контракт задания субагенту

Каждое задание должно отвечать на пять вопросов:

```text
Target: какие файлы и символы относятся к срезу?
Change/Question: какое наблюдаемое поведение нужно получить или исследовать?
Contract: какие интерфейсы и инварианты уже зафиксированы?
Non-goals: чего нельзя касаться?
Acceptance: каким наблюдением определяется успех?
```

Пример плохого задания:

```text
Посмотри auth и поправь проблемы.
```

Пример хорошего:

```text
Target: src/http/session.ts и прямые callers функции parseSession.
Change: возвращать InvalidSession для истёкшей подписи до загрузки пользователя.
Contract: сигнатура parseSession и формат cookie неизменны.
Non-goals: refresh flow, OAuth providers, logging.
Acceptance: существующий CLI reproduction с истёкшей cookie возвращает 401;
валидная cookie продолжает возвращать 200.
```

## Волны и барьеры

### Волна 1: разведка

Запускайте столько scouts, сколько существует независимых вопросов. Обычно 3–8 достаточно. Каждый получает один subsystem или одну гипотезу.

### Барьер 1: синтез

Основная модель:

- удаляет дубли;
- сопоставляет пересекающиеся call/data flows;
- проверяет противоречия;
- читает decision-critical участки;
- фиксирует реализационный контракт.

### Волна 2: реализация

Workers получают непересекающиеся ownership-зоны. Если два задания должны менять один файл или exported symbol, это один срез, а не два.

### Барьер 2: интеграция

Основная модель проверяет:

- совместимость интерфейсов;
- все references публичных символов;
- отсутствие старого пути после clean cutover;
- поведение полного пользовательского сценария.

### Волна 3: review

Разделяйте review по рискам, а не дублируйте одинаковое «посмотри код»:

- correctness/state transitions;
- API compatibility/callsites;
- security/trust boundaries;
- concurrency/lifecycle;
- resources/performance.

## Когда остановить fan-out

Не добавляйте агентов, если следующий агент:

- повторяет уже назначенную область;
- не имеет собственного проверяемого вопроса;
- зависит от незавершённого решения;
- создаёт больше интеграционной работы, чем выполняет;
- нужен только для подтверждения мнения без нового evidence.

Оптимальная ширина определяется числом независимых срезов, а не числом файлов или доступным лимитом параллелизма.

## Защита от слабых отчётов

Основная модель должна перепроверять утверждение, если оно:

- определяет архитектурное решение;
- ведёт к удалению кода;
- меняет публичный API или schema;
- получает high severity;
- противоречит другому агенту;
- основано на inference без исполнения;
- зависит от версии внешней библиотеки.

Остальные точные факты с `file:line` можно проверять выборочно.
