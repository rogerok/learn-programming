# Расследование и исправление багов

## Принцип

Для бага параллелизируются **независимые гипотезы причины**, а не случайные файлы. Исправление начинается только после воспроизведения и выбора подтверждённой гипотезы.

## Волна 1: зафиксировать симптом

Основная модель определяет:

- точные входы;
- ожидаемое поведение;
- фактическое поведение;
- минимальную среду;
- воспроизводимость;
- момент, где наблюдение впервые расходится с ожиданием.

`cheap-verifier` можно поручить запуск уже известного безопасного reproduction, но не поиск причины.

## Волна 2: проверить гипотезы

Возможные независимые направления:

- parsing/validation входа;
- state transition и порядок событий;
- storage/cache consistency;
- race/lifecycle;
- версия или semantics внешней зависимости;
- platform-specific path;
- error mapping на API boundary.

Каждая гипотеза получает отдельного `cheap-scout`; внешняя semantics — `cheap-librarian`.

## Полный запрос

```text
Расследуй баг по схеме reproduce → parallel hypotheses → fix source → reproduce again.

Сначала сам сформулируй наблюдаемый контракт и минимальный reproduction.
Если сценарий уже известен и безопасен, передай его cheap-verifier и потребуй точные
команды, входы и результат.

Затем сам выдели независимые гипотезы причины. Параллельно назначь cheap-scout
на каждую гипотезу. Каждый должен собрать evidence за и против гипотезы,
указать первый ошибочный state transition и предложить минимальную решающую проверку.

Не разрешай workers вносить изменения до выбора подтверждённой причины.
После синтеза сам выбери root cause, опиши инвариант исправления и только затем
передай независимый механический срез cheap-worker либо исправь связанный код сам.

В конце повтори тот же reproduction с теми же входами и проверь ближайший
регрессионный сценарий. Не подменяй runtime reproduction статическим чтением или тестом,
который не проходит через дефектный путь.
```

## Формат гипотезы

```text
Hypothesis: конкретный механизм причины.
Prediction: что ещё должно наблюдаться, если она верна.
Evidence for: file:line или execution output.
Evidence against: file:line или execution output.
Decisive check: минимальная проверка, различающая эту гипотезу от альтернатив.
```

Такой формат защищает от типичной ошибки дешёвой модели: найти подозрительную строку и сразу объявить её root cause.

## Кейс: intermittent bug

Для нестабильного сбоя разделите работу:

1. `cheap-verifier` — точное воспроизведение, частота и окружение;
2. `cheap-scout` — ownership общего mutable state;
3. `cheap-scout` — lifecycle ресурсов и отмена;
4. `cheap-scout` — ordering/locking/async boundaries;
5. `cheap-librarian` — гарантии concurrency используемого runtime или клиента.

Основная модель сопоставляет временную последовательность. Отдельные отчёты без общей timeline недостаточны.

## Кейс: регрессия после обновления зависимости

```text
Параллельно:
- cheap-scout локализует adapter и assumptions проекта;
- cheap-librarian сравнивает changelog, migration guide и upstream implementation
  между старой и новой точными версиями;
- cheap-verifier выполняет минимальный сценарий на текущей версии.

Сам установи, нарушился ли наш инвариант, upstream contract или adapter.
Исправляй adapter/usage, а не маскируй upstream error.
```

## Когда не нужен worker

Если root cause пересекает общий state, публичный API или несколько тесно связанных компонентов, сильной основной модели безопаснее исправить его самой. Делегирование edit оправдано только после превращения решения в механический независимый срез.
