# Исследование репозитория и обучение

## Цель

Быстро построить достоверную карту незнакомого проекта, не заставляя дорогую основную модель последовательно читать весь репозиторий.

## Подходящие срезы

Пример исследовательского fan-out:

1. entry points и lifecycle приложения;
2. HTTP/API boundary;
3. модель данных и persistence;
4. authentication/authorization;
5. фоновые jobs и очереди;
6. build, deployment и configuration;
7. тестовая стратегия и локальные способы запуска.

Каждый срез назначается отдельному `cheap-scout`. Внешнюю документацию ключевого фреймворка или протокола отдайте `cheap-librarian`.

## Запрос

```text
Изучи этот репозиторий по схеме cheap fan-out → strong synthesis.

Сам сначала определи 4–7 независимых архитектурных вопросов. Параллельно назначь
по одному cheap-scout на каждый вопрос. Если понимание зависит от внешней библиотеки,
назначь отдельного cheap-librarian на точную версию из manifest/lockfile.

Scouts должны вернуть entry points, ключевые symbols, call/data flow, file:line,
unknowns и confidence. Они не должны редактировать файлы и давать общий архитектурный вывод.

После fan-out сам:
- сопоставь пересечения;
- перепроверь через LSP ключевые границы;
- построй единую карту request/data lifecycle;
- перечисли безопасные точки расширения;
- явно отметь неизвестное и не подтверждённые inference.
```

## Ожидаемый итог основной модели

```text
1. Как запускается система.
2. Главные компоненты и их ответственность.
3. Один сквозной пользовательский/request flow.
4. Где создаётся, преобразуется и сохраняется state.
5. Trust boundaries и внешние зависимости.
6. Места, которые нужно менять для конкретной будущей задачи.
7. Unknowns и точные способы их проверить.
```

Это должен быть единый синтез, а не склейка отчётов агентов.

## Учебный кейс: понять один механизм

Например, нужно разобраться, как работает кеширование:

```text
Параллельно используй cheap-scout для трёх вопросов:
1. где кеш создаётся и конфигурируется;
2. кто читает и инвалидирует записи;
3. какие тесты или runtime paths показывают поведение при miss/stale/error.
Отдельному cheap-librarian передай проверку semantics используемой cache library
для точной версии проекта.

Сам объедини local implementation и upstream semantics в одну модель состояний.
Каждое состояние и переход привяжи к коду или первичному источнику.
```

## Учебный кейс: сравнить теорию и реализацию

```text
Выдели один cheap-scout для реализации паттерна в репозитории и один
cheap-librarian для канонического описания паттерна. Запусти их параллельно.
Сам сравни:
- какие свойства паттерна реально присутствуют;
- какие отсутствуют;
- какие отличия вызваны требованиями проекта;
- где название паттерна вводит в заблуждение.
Не оценивай код только по совпадению терминологии.
```

## Типичные ошибки

### Делить по директориям без вопроса

Директория может не совпадать с архитектурной границей. Назначайте агенту flow или ответственность, а не просто путь.

### Просить каждого описать всю архитектуру

Получатся дубли и противоречивые глобальные модели. Каждый scout исследует только локальную область; глобальную модель строит координатор.

### Не фиксировать версию внешней зависимости

Документация latest может не соответствовать lockfile. `cheap-librarian` должен начать с manifest/lockfile.

### Принимать отсутствие grep-результата за отсутствие поведения

Код может использовать re-export, generated bindings, macro, dynamic registration или framework convention. Decision-critical absence нужно проверить LSP, build metadata или исполнением.
