# Практика: распознавание, инварианты и перенос

Вернитесь к [[MOC|карте раздела]], если выбор алгоритма пока определяется названием задачи, а не свойствами входа. Во всех упражнениях сначала сохраните письменный прогноз и ручную трассировку. Код запускайте только после этапов `predict` и `explain`.

Общий формат отчёта для каждого упражнения:

1. выбранный паттерн и отвергнутая альтернатива;
2. инвариант и условие завершения;
3. заполненная трассировочная таблица;
4. оценка времени и дополнительной памяти;
5. реализация и результаты проверок;
6. найденный дефект и первая строка, где трассировка расходится с ожиданием;
7. ответ на вопрос переноса и рефлексию.

## 1. Бинарный поиск: диапазон кандидатов

**Результат:** распознать применимость бинарного поиска, объяснить инвариант границ и диагностировать шаг, который не уменьшает диапазон.

**Предварительные знания:** [[grocking-algorithms/1.meet-algorithms/1.meet-algorithms|Big O]] и [[grocking-algorithms/1.meet-algorithms/binary-search|бинарный поиск]].

### Predict

Для каждого входа решите, допустим ли бинарный поиск, и назовите проверяемое свойство входа:

1. `[-3, 1, 4, 7, 9, 12, 18]`, найти `9`;
2. `[7, 1, 9, 4]`, найти `9`;
3. `[{ id: 2 }, { id: 5 }, { id: 8 }]`, найти объект с `id === 5`.

До запуска кода заполните таблицу для первого входа. В столбце «оставшиеся кандидаты» записывайте диапазон индексов после сравнения.

| Итерация | `low` до шага | `high` до шага | `mid` | `list[mid]` | Сравнение | Оставшиеся кандидаты |
|---:|---:|---:|---:|---:|---|---|
| 1 |  |  |  |  |  |  |
| 2 |  |  |  |  |  |  |
| 3 |  |  |  |  |  |  |
| 4 |  |  |  |  |  |  |

### Explain

Сформулируйте инвариант через `low`, `high` и возможное положение `target`. Затем объясните:

- почему отсортированность нужна именно для отбрасывания половины диапазона;
- почему после неравного сравнения индекс `mid` нельзя оставлять среди кандидатов;
- какая целочисленная мера строго уменьшается на каждой итерации.

### Modify

Возьмите итеративный вариант из конспекта и сначала измените только его контракт: не найденное значение должно возвращать `-1`, а пустой массив не должен требовать отдельного прохода. Не добавляйте линейный поиск как запасной путь.

### Implement

Напишите `binarySearch(list, target)` самостоятельно по своему инварианту. Проверки детерминированы:

```js
binarySearch([-3, 1, 4, 7, 9, 12, 18], 9) === 4;
binarySearch([-3, 1, 4, 7, 9, 12, 18], -3) === 0;
binarySearch([-3, 1, 4, 7, 9, 12, 18], 18) === 6;
binarySearch([-3, 1, 4, 7, 9, 12, 18], 5) === -1;
binarySearch([], 5) === -1;
```

**Приёмка:** все проверки истинны; на каждой неуспешной итерации длина диапазона `[low, high]` уменьшается; решение не использует `indexOf`, `find`, `findIndex` или дополнительный массив; в отчёте обоснованы `O(log n)` времени и `O(1)` дополнительной памяти.

### Diagnose

Не исправляя код сразу, вручную проследите вход `list = [1, 3]`, `target = 3` для такого обновления:

```js
if (list[mid] < target) {
  low = mid;
}
```

Запишите первую повторившуюся пару `(low, high)`, укажите нарушенное условие прогресса и только затем внесите минимальную правку в свою реализацию.

### Transfer

Массив отсортирован, но нужно вернуть индекс позиции, куда можно вставить отсутствующий `target`, не нарушив порядок. Объясните, какие границы и инвариант бинарного поиска сохраняются, а что должно означать состояние после завершения цикла. Реализация этого переноса необязательна.

</details>

<details>
<summary>Подсказка 2</summary>

Для диагностики отдельно вычислите `mid` при `low = 0`, `high = 1`, а затем повторите вычисление после ветки `list[mid] < target`.

</details>

## 2. BFS: ближайший узел в невзвешенном графе

**Результат:** распознать задачу на BFS, объяснить связь `FIFO` с расстоянием и предотвратить повторную обработку узлов.

**Предварительные знания:** [[grocking-algorithms/6.breadth-first-search/6.breadth-first-search|графы, очередь и BFS]].

Используйте фиксированный порядок соседей:

```js
const graph = {
  A: ["B", "C"],
  B: ["D"],
  C: ["D", "E"],
  D: ["F"],
  E: [],
  F: ["B"],
};
```

### Predict

До кода предскажите порядок первого посещения узлов от `A` и ответ для целей `E`, `F` и `Z`. Заполняйте строку после извлечения `current` и добавления ещё не обнаруженных соседей.

| Шаг | `current` | Очередь после шага | Обнаруженные узлы | Расстояние от `A` |
|---:|---|---|---|---:|
| 1 |  |  |  |  |
| 2 |  |  |  |  |
| 3 |  |  |  |  |
| 4 |  |  |  |  |
| 5 |  |  |  |  |
| 6 |  |  |  |  |

### Explain

Запишите инвариант, связывающий начало очереди с расстоянием от `A`. Объясните, почему:

- `Stack` не гарантирует тот же порядок уровней;
- узел нужно помечать обнаруженным не позднее его добавления в очередь;
- цикл `F → B → D → F` не приводит корректную реализацию к бесконечному обходу.

### Modify

Преобразуйте идею `findMangoSeller` из конспекта: вместо проверки имени принимайте конкретный `target`, вместо вывода возвращайте `true` или `false`. Сохраните `FIFO` и защиту от повторного добавления.

### Implement

Реализуйте `hasPathBfs(graph, source, target)` без рекурсии. Проверки:

```js
hasPathBfs(graph, "A", "E") === true;
hasPathBfs(graph, "A", "F") === true;
hasPathBfs(graph, "E", "A") === false;
hasPathBfs(graph, "A", "Z") === false;
hasPathBfs(graph, "A", "A") === true;
```

**Приёмка:** проверки истинны; каждый существующий узел добавляется в очередь не более одного раза; неизвестная цель возвращает `false`; в отчёте сложность выражена через количество вершин `V` и рёбер `E`; ручной порядок согласуется с фактическим журналом посещений.

### Diagnose

Удалите защиту `Set` только мысленно и продолжите таблицу после достижения `F`. Найдите первый повторно добавленный узел и покажите цикл состояний очереди. После этого рассмотрите вариант, где узел отмечается только при извлечении: объясните, почему `D` может оказаться в очереди дважды ещё до первого извлечения.

### Transfer

Для дерева каталогов требуется вывести файлы либо по уровням вложенности, либо полностью обработать подкаталог сразу после обнаружения. Выберите BFS или DFS для каждого требования и свяжите выбор с порядком хранения ожидающих каталогов.

<summary>Подсказка 1</summary>

Подпишите каждому узлу его минимальное число рёбер от `A`, прежде чем заполнять очередь.

## 3. Stack: обратный порядок остатков

**Результат:** распознать необходимость `LIFO`, объяснить инвариант двух фаз и диагностировать переменную, которая не приближает цикл к завершению.

**Предварительные знания:** [[learning-js-data-structure-and-algs/stack|Stack и преобразование систем счисления]].

### Predict

Для `decNumber = 10`, `base = 2` вручную заполните первую фазу. В строке показывайте стек после `push` слева направо от дна к вершине.

| Шаг | `decNum` до деления | Остаток | `decNum` после деления | Стек |
|---:|---:|---:|---:|---|
| 1 |  |  |  |  |
| 2 |  |  |  |  |
| 3 |  |  |  |  |
| 4 |  |  |  |  |

Затем предскажите последовательность `pop` и итоговую строку.

### Explain

Сформулируйте два инварианта: один для цикла деления, второй для цикла сборки строки. Объясните, почему остатки возникают от младшего разряда к старшему, а читать результат нужно в обратном порядке.

### Modify

Измените контракт `baseConverter(decNumber, base)` так, чтобы вход `0` возвращал строку `"0"`. Остальной алгоритм и диапазон оснований `2..16` оставьте прежними.

### Implement

Реализуйте преобразование через `Stack`, не используя `Number.prototype.toString` и `reverse`.

```js
baseConverter(10, 2) === "1010";
baseConverter(31, 16) === "1F";
baseConverter(8, 8) === "10";
baseConverter(0, 2) === "0";
```

**Приёмка:** проверки истинны; каждая итерация первой фазы уменьшает `decNum`; число `push` равно числу `pop` для положительного входа; используются цифры `0123456789ABCDEF`; обоснованы `O(log_base n)` времени и памяти.

### Diagnose

В конспектном варианте встречается обновление:

```js
decNum = Math.floor(decNumber / base);
```

Проследите две итерации для `(10, 2)`, назовите первую переменную, которая неожиданно перестаёт изменяться, и объясните, какое условие завершения из-за этого недостижимо. Исправление внесите только после трассировки.

### Transfer

Предложите, как тем же `Stack` обратить порядок токенов `['a', 'b', 'c']`. Не пишите второй алгоритм полностью: перечислите операции и укажите, какой инвариант из преобразования числа сохраняется.

</details>

<details>
<summary>Подсказка 2</summary>

## 4. Дерево: выбор порядка обхода

**Результат:** различить BFS и DFS дерева по требуемому порядку, объяснить инвариант ожидающих узлов и диагностировать ошибку обхода каталога.

**Предварительные знания:** [[recursion/recursion|рекурсия]] и [[grocking-algorithms/7.trees/7.trees|деревья, BFS и DFS]].

Используйте дерево:

```text
A
├── B
│   ├── D
│   └── E
└── C
    └── F
```

### Predict

Запишите без кода:

- порядок BFS при обходе соседей слева направо;
- порядок рекурсивного DFS pre-order при том же порядке соседей;
- содержимое очереди BFS после обработки `A`, `B` и `C`;
- последовательность активных рекурсивных вызовов до первого достижения `E`.

Ручная таблица BFS:

| Шаг | Посещённый узел | Очередь до добавления детей | Очередь после добавления детей |
|---:|---|---|---|
| 1 |  |  |  |
| 2 |  |  |  |
| 3 |  |  |  |
| 4 |  |  |  |
| 5 |  |  |  |
| 6 |  |  |  |

### Explain

Для BFS сформулируйте инвариант очереди по уровням. Для рекурсивного DFS укажите, что хранит call stack и почему выполнение возвращается к родителю после листа. Объясните, почему отсутствие циклов в дереве позволяет не хранить `Set`, но тот же код нельзя без проверки переносить на произвольный граф.

### Modify

Измените контракт конспектных обходов: вместо `console.log` функции должны возвращать массив имён в порядке посещения. Это изменение касается накопления результата, но не порядка обхода.

### Implement

Реализуйте для объектного представления дерева две функции: `bfsOrder(tree, source)` и `dfsPreOrder(tree, source)`.

```js
const tree = {
  A: ["B", "C"],
  B: ["D", "E"],
  C: ["F"],
  D: [],
  E: [],
  F: [],
};

bfsOrder(tree, "A").join("") === "ABCDEF";
dfsPreOrder(tree, "A").join("") === "ABDECF";
```

**Приёмка:** обе проверки истинны; каждый узел посещён ровно один раз; фактический порядок совпадает с предварительным прогнозом; BFS использует очередь, DFS — рекурсивный переход; для обеих реализаций обоснованы `O(V)` времени и `O(V)` памяти в худшем случае.

### Diagnose

