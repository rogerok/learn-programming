# Упражнения по JavaScript Core и Async

## Как работать

Создавайте отдельный `.js` или `.mjs`-файл для каждого задания. Сначала фиксируйте прогноз или объяснение, затем запускайте код и сравнивайте наблюдение с моделью. Здесь нет готовых реализаций: критерии описывают поведение, которое должен увидеть вызывающий код.

Порядок обязателен: **Predict → Explain → Modify → Implement → Diagnose → Transfer**. Если проверка не проходит, вернитесь к связанным заметкам, а не переходите к следующей ступени.

## 1. Predict — независимые closure

**Результат:** предсказать состояние двух независимо созданных closure и связать каждое изменение со своим lexical environment.

**Пререквизиты:** [[functions/closure|closure]], [[syntax/statements-vs-expressions|выражения и инструкции]].

Не запускайте код до письменного прогноза:

```js
const makeCounter = (start) => {
  let value = start;

  return (step = 1) => {
    value += step;
    return value;
  };
};

const first = makeCounter(2);
const second = makeCounter(10);

console.log(first(), first(3), second(), first());
```

### Наблюдаемая приёмка

- Записаны четыре значения `console.log` в правильном порядке.
- Для каждого значения указано, какой вызов изменил `value` и к какому экземпляру окружения он относится.
- Объяснение не опирается на фразу «функция запомнила» без указания места объявления и отдельного вызова `makeCounter`.

### Проверка

1. Сохраните прогноз.
2. Запустите файл через `node` ровно один раз.
3. При несовпадении нарисуйте два отдельных environment record и повторите прогноз с другим `start`.

> [!hint]- Подсказка 1
> Считайте каждый вызов `makeCounter` созданием нового локального `value`.

> [!hint]- Подсказка 2
> Вызов `second()` не может изменить переменную, которую использует `first`.

### Рефлексия

Как изменился бы жизненный цикл `value`, если бы `makeCounter` возвращал число, а не функцию?

## 2. Explain — порядок выполнения

**Результат:** объяснить наблюдаемый порядок через текущий call stack и очередь timer-callback, а не через длительность задержки.

**Пререквизиты:** [[async/1.theory-unit|событийная модель]], [[async/2.call-stack|call stack и event loop]], [[async/8.timers|timers]].

```js
console.log("start");

setTimeout(() => {
  console.log("timer");
}, 0);

console.log("finish");
```

### Наблюдаемая приёмка

- До запуска записан предполагаемый порядок трёх строк.
- Для каждой строки указано, выполняется она в текущем стеке или в отдельном вызове после опустошения стека.
- Значение `0` объяснено как минимальная задержка постановки callback, а не гарантия немедленного вызова.

### Ручные checkpoints

- Сразу после регистрации timer: где находится callback и занят ли текущий стек?
- Перед последним синхронным `console.log`: может ли event loop уже поместить timer-callback в занятый стек?
- После завершения файла: какое условие позволяет выполнить callback?

> [!hint]- Подсказка 1
> Вызов `setTimeout` и выполнение переданной функции — разные события.

> [!hint]- Подсказка 2
> Event loop передаёт callback на выполнение только тогда, когда текущий стек пуст.

### Рефлексия

Почему увеличение delay может отложить callback, но уменьшение delay до нуля не позволяет прервать выполняющийся синхронный код?

## 3. Modify — error-first callback

**Результат:** изменить wrapper так, чтобы он сохранял error-first контракт, не обращался к отсутствующим данным и вызывал callback ровно один раз.

**Пререквизиты:** [[async/3.asynchronous-code|callback-based async]], [[async/4.asynchronous-return|async return]], [[async/6.error-handling|обработка ошибок]].

Исходная версия намеренно теряет ошибку:

```js
import { readFile } from "node:fs";

const readTrimmed = (path, callback) => {
  readFile(path, "utf8", (_error, data) => {
    callback(null, data.trim());
  });
};
```

Измените только внутренний callback и сохраните публичную сигнатуру `readTrimmed(path, callback)`.

### Наблюдаемая приёмка

- Для существующего файла callback получает `null` и строку без внешних пробелов.
- Для отсутствующего файла первый аргумент callback — исходный `Error`, а результата нет.
- В обеих ветках callback вызывается ровно один раз.
- `readTrimmed` не пытается синхронно вернуть содержимое файла и не бросает новую ошибку вместо исходной.

### Проверка

Создайте временный текстовый файл с пробелами по краям и отдельный несуществующий путь. В проверочном callback считайте число вызовов и печатайте только форму результата: `success/error`, тип второго аргумента и счётчик. Удалите временный файл после проверки.

> [!hint]- Подсказка 1
> Первое действие внутреннего callback — проверить `error`, до обращения к `data`.

> [!hint]- Подсказка 2
> После передачи ошибки нужен ранний выход, иначе success-ветка вызовет callback повторно.

> [!hint]- Подсказка 3
> В success-ветке сохраняется соглашение `(null, result)`.

### Рефлексия

Как вызывающий код отличит пустой файл от ошибки чтения, если wrapper передаёт только один аргумент?

## 4. Implement — последовательная Promise-цепочка

**Результат:** реализовать выполнение массива lazy-задач строго по очереди с накоплением результатов и наблюдаемым reject.

**Пререквизиты:** [[async/9.promise|Promise]], [[async/10.promise-catch|Promise errors]], [[async/11.chain-of-promise|динамическая цепочка]].

Контракт:

```js
const sequence = (tasks) => {
  // tasks: Array<() => Promise<unknown>>
  // вернуть Promise с массивом результатов в исходном порядке
};
```

Не меняйте `tasks` на массив уже запущенных Promise: каждая задача должна оставаться функцией до своего шага.

### Наблюдаемая приёмка

- Пустой массив даёт fulfilled Promise со значением `[]`.
- Следующая задача стартует только после выполнения предыдущей.
- Результаты сохраняют порядок `tasks`, даже если внутренние задержки различаются.
- Первый reject останавливает запуск ещё не начатых задач и остаётся доступен внешнему `catch`.
- `sequence` всегда возвращает Promise.

### Ручные checkpoints

Используйте три task-функции, каждая записывает `start:<id>` при вызове и `finish:<id>` перед resolve. После завершения сравните журнал с последовательными парами `start/finish`. Затем замените среднюю задачу на rejected Promise и убедитесь, что журнал не содержит старта третьей.

> [!hint]- Подсказка 1
> Начальное состояние цепочки может быть fulfilled Promise с пустым массивом.

> [!hint]- Подсказка 2
> На каждом шаге accumulator должен оставаться Promise, а task вызывается внутри `then`, не заранее.

> [!hint]- Подсказка 3
> Верните Promise текущей task из `then`; её результат добавляйте без изменения предыдущего массива до выполнения task.

### Рефлексия

Когда последовательность здесь является требованием корректности, а когда независимые задачи разумнее запустить конкурентно?

## 5. Diagnose — потерянный Promise

**Результат:** найти границы, на которых Promise перестаёт быть наблюдаемым, и восстановить единый канал результата и ошибки.

**Пререквизиты:** [[async/9.promise|then возвращает новый Promise]], [[async/10.promise-catch|распространение reject]], [[async/11.chain-of-promise|непрерывность цепочки]].

```js
const loadPair = (load, left, right) => {
  load(left).then((leftValue) => {
    load(right).then((rightValue) => [leftValue, rightValue]);
  });
};

loadPair(loadValue, "left", "right")
  .then(console.log)
  .catch(console.error);
```

Считайте, что `loadValue(key)` всегда возвращает Promise и может reject. Найдите все места, где вызывающий код теряет контроль, и исправьте их без добавления локального `catch`, подавляющего ошибку.

### Наблюдаемая приёмка

- `loadPair` немедленно возвращает Promise.
- При успехе Promise выполняется парой значений в порядке `left`, `right`.
- Reject любого `load` достигает внешнего `catch` с исходной ошибкой.
- Внешний `then` не запускается до завершения обоих чтений.

### Проверка

Подставьте три fake-реализации `loadValue`: обе ветки успешны; reject первого ключа; reject второго ключа. Для каждого случая запишите, какой внешний обработчик сработал и сколько вызовов `load` произошло.

> [!hint]- Подсказка 1
> Сначала проверьте значение, которое возвращает сама `loadPair`.

> [!hint]- Подсказка 2
> Вложенный `then` создаёт Promise; внешний `then` сможет ждать его только через явный возврат.

### Рефлексия

Почему добавление `catch(console.error)` внутрь `loadPair` может превратить ошибку в успешное выполнение со значением `undefined`?

## 6. Transfer — управляемый async-pipeline

**Результат:** перенести правила closure, чистых преобразований, последовательной Promise-цепочки и проброса ошибок в новый pipeline с внедрёнными эффектами.

**Пререквизиты:** все предыдущие задания, [[functions/pure-functions|чистые функции]], [[functions/cqs|CQS]], [[async/11.chain-of-promise|Promise chain]].

Спроектируйте функцию:

```js
const createOrderedProcessor = ({ load, transform, save }) => {
  // вернуть функцию process(ids)
};
```

Контракт зависимостей:

- `load(id)` возвращает Promise с записью;
- `transform(record)` — синхронная чистая функция;
- `save(record)` возвращает Promise с сохранённой записью;
- `process(ids)` возвращает Promise с массивом сохранённых записей.

### Наблюдаемая приёмка

- `ids` обрабатываются строго последовательно: `load → transform → save` для одного id завершается до `load` следующего.
- `transform` не знает об I/O и не изменяет исходную запись.
- Результаты находятся в порядке `ids`.
- Reject из `load` или `save`, а также исключение из `transform` прекращает последующие шаги и достигает вызывающего кода.
- Пустой `ids` выполняется значением `[]` без вызова зависимостей.
- Для проверки достаточно fake-зависимостей; реальная файловая система или сеть не требуется.

### Ручные checkpoints

1. До кода запишите границы query, чистого преобразования и command.
2. Fake-зависимости добавляют события в журнал; для двух id ожидается отсутствие пересечения шагов.
3. Вставьте ошибку по второму id и убедитесь, что журнал не содержит третьего id.
4. Повторно вызовите созданный processor и проверьте, что журнал и результаты одного запуска не протекают в другой.

> [!hint]- Подсказка 1
> В closure фабрики должны остаться зависимости, но состояние конкретного запуска лучше создавать внутри `process`.

> [!hint]- Подсказка 2
> Последовательный каркас уже сформулирован в задании Implement; здесь один task состоит из трёх зависимых этапов.

> [!hint]- Подсказка 3
> Синхронное исключение внутри `then` автоматически становится reject возвращаемого этим `then` Promise, если цепочка не разорвана.

### Рефлексия

Какие части контракта пришлось бы изменить для конкурентной обработки с сохранением порядка результатов и ограничением числа одновременно выполняемых операций?
