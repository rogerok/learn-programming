# Упражнения по OOP

Задания идут по нарастающей: **предсказать → объяснить → изменить → реализовать → диагностировать → перенести**. Сначала зафиксируйте ответ, затем запускайте проверку. Готовое решение не сверяйте с названием принципа: проверяйте наблюдаемое поведение.

## 1. Предскажите идентичность и мутации

**Результат:** вы отличаете новую ссылку, новый внешний объект и общую вложенную ссылку.

**Предварительно:** [[objects/objects|объекты и поверхностное копирование]].

Не запускайте код сразу. Для каждого `console.log` запишите ожидаемое значение и объяснение одним предложением.

```js
const profile = {
  name: "Ada",
  settings: { theme: "dark" },
};

const alias = profile;
const clone = Object.assign({}, profile);

clone.name = "Grace";
clone.settings.theme = "light";

console.log(profile === alias);
console.log(profile === clone);
console.log(profile.name);
console.log(alias.settings.theme);
console.log(clone.settings === profile.settings);
```

**Наблюдаемые требования:**

- заполнена таблица из пяти прогнозов до запуска;
- для каждого результата указано, сравнивается идентичность или читается состояние;
- объяснено, почему изменение `name` и изменение `settings.theme` распространяются по-разному.

**Проверка:** сохраните фрагмент как `identity.js`, выполните `node identity.js`, сопоставьте все пять строк с прогнозом. Если прогноз расходится хотя бы в одной строке, нарисуйте объекты и стрелки ссылок и повторите объяснение.

> [!hint]- Подсказка 1
> Оператор `===` для объектов сравнивает не содержимое, а идентичность.

> [!hint]- Подсказка 2
> `Object.assign({}, source)` создаёт новый объект только на верхнем уровне.

> [!hint]- Подсказка 3
> Нарисуйте отдельно три переменные, два внешних объекта и один объект `settings`; соедините их стрелками до чтения результатов.

**Рефлексия:** где в реальном API поверхностная копия могла бы создать ложное ощущение изоляции состояния?

## 2. Объясните контракт допустимого состояния

**Результат:** вы превращаете набор необязательных полей в явный поведенческий контракт.

**Предварительно:** [[abstractions/invariants|инварианты]], [[abstractions/interfaces|интерфейсы как контракт]].

Рассмотрите модель загрузки:

```ts
type LoadState<T> = {
  loading: boolean;
  data?: T;
  error?: Error;
};
```

Опишите состояния `loading`, `success` и `error` без реализации функций. Для каждого состояния укажите обязательные и запрещённые поля, допустимые переходы и то, что вправе предполагать клиент после проверки состояния. Затем предложите публичный TypeScript-контракт, в котором запрещённые комбинации нельзя создать без обхода системы типов.

**Наблюдаемые требования:**

- перечислены ровно три допустимых варианта и не менее трёх недопустимых комбинаций;
- для каждого варианта записан инвариант;
- переходы образуют понятный граф, включая повторную загрузку;
- клиенту не нужны вложенные проверки `loading`, `data` и `error`;
- контракт не содержит одновременно независимый `loading: boolean` и необязательные `data`/`error` как единственный способ различения вариантов.

**Ручная проверка:** возьмите комбинации `{ loading: false }`, `{ loading: true, data }` и `{ loading: false, data, error }`. Для каждой покажите конкретное место в предложенном контракте, из-за которого TypeScript должен её отвергнуть.

> [!hint]- Подсказка 1
> Начните с таблицы: имя состояния, обязательные данные, запрещённые данные.

> [!hint]- Подсказка 2
> Один литеральный признак может различать несколько вариантов union.

> [!hint]- Подсказка 3
> После `switch` по признаку тип каждого варианта должен сужаться без `as` и `!`.

**Рефлексия:** какой инвариант здесь обеспечивает тип, а какой всё равно должна обеспечить функция, выполняющая переход?

## 3. Измените границу инкапсуляции

**Результат:** `Rectangle` и `Database` сохраняют инварианты на всех публичных путях чтения и записи.

**Предварительно:** [[concepts/encapsulation/encapsulation|примеры Rectangle и Database]], [[abstractions/invariants|инварианты]].

Возьмите оба класса из заметки об инкапсуляции и измените их, не меняя предметный смысл:

1. У `Rectangle` ширина и высота всегда положительны. Конструктор и последующие присваивания нормализуют неположительное значение до `1`; доступны `width`, `height` и вычисляемый `perimeter`.
2. `Database` разрешает добавлять и очищать таблицы только своими методами. Получатель `tables` не должен позволять внешнему коду изменить внутренний массив или его элементы.

**Наблюдаемые требования:**

- недопустимый размер нельзя наблюдать сразу после конструктора или после присваивания;
- правило размера записано в одном месте либо все пути записи явно доказаны одинаковыми тестами;
- мутация значения, полученного из `db.tables`, не меняет последующее значение `db.tables`;
- одного `readonly` в сигнатуре недостаточно, если во время выполнения наружу всё ещё возвращается та же изменяемая ссылка;
- публичный код не обращается к `private`-полям через приведение типов.

**Запускаемая проверка:** адаптируйте импорт или поместите проверки после своих классов.

```ts
import assert from "node:assert/strict";

const rectangle = new Rectangle(-2, 3);
assert.equal(rectangle.width, 1);
assert.equal(rectangle.height, 3);
rectangle.height = 0;
assert.equal(rectangle.height, 1);
assert.equal(rectangle.perimeter, 4);

const db = new Database("user", "secret", "5432", "localhost");
db.createNewTable(["users"]);
const observed = db.tables as unknown as string[][];
observed.push(["injected"]);
observed[0].push("injected-column");
assert.deepEqual(db.tables, Array.of(["users"]));
db.clearTables();
assert.deepEqual(db.tables, []);
```

Запустите файл выбранным в разделе способом запуска TypeScript. При необходимости уточните тип `Table`, но не ослабляйте проверки через `any`.

Приведение через `unknown` в проверке имитирует недоверенный JavaScript-клиент: типовая защита не заменяет защиту инварианта во время выполнения.

> [!hint]- Подсказка 1
> Проверьте отдельно вход через конструктор, вход через setter и выход через getter.

> [!hint]- Подсказка 2
> Конструктор может использовать тот же путь проверки, что и последующая запись.

> [!hint]- Подсказка 3
> Копия только внешнего массива не защищает вложенные изменяемые массивы. Подумайте о копировании на границе или о неизменяемом представлении таблицы.

**Рефлексия:** какую цену по памяти и времени платит защитное копирование и когда вместо него лучше изменить модель данных?

## 4. Реализуйте заменяемую стратегию комиссии

**Результат:** платёжный объект делегирует расчёт комиссии подменяемой зависимости и не знает конкретных стратегий.

**Предварительно:** [[concepts/interfaces/interfaces|интерфейсы]], [[concepts/composition/composition|композиция]], [[polymorphism/6.factory-strategy|Strategy]].

Реализуйте контракты `FeeStrategy` и `PaymentMethod`, стратегии `NoFee`, `PercentageFee`, `FixedFee` и класс `CardPayment`. Метод `pay(amount)` возвращает объект `{ subtotal, fee, total }`. Стратегия передаётся в `CardPayment` через конструктор.

**Наблюдаемые требования:**

- `CardPayment` не содержит `switch`, `instanceof` или сравнения имени стратегии;
- процентная стратегия получает ставку при создании, фиксированная — сумму комиссии;
- `total === subtotal + fee` для каждой реализации;
- новую стратегию можно добавить без изменения `CardPayment`;
- поведение для отрицательной суммы явно определено контрактом и одинаково для всех стратегий: отклонение до делегирования либо единая поддержка.

**Запускаемая проверка:** используйте эти сценарии; выберите и добавьте один `assert.throws` либо один положительный `assert` для согласованного поведения отрицательной суммы.

```ts
import assert from "node:assert/strict";

assert.deepEqual(
  new CardPayment(new NoFee()).pay(200),
  { subtotal: 200, fee: 0, total: 200 },
);
assert.deepEqual(
  new CardPayment(new PercentageFee(0.1)).pay(200),
  { subtotal: 200, fee: 20, total: 220 },
);
assert.deepEqual(
  new CardPayment(new FixedFee(15)).pay(200),
  { subtotal: 200, fee: 15, total: 215 },
);
```

> [!hint]- Подсказка 1
> Клиенту достаточно знать операцию `calculate(amount): number`.

> [!hint]- Подсказка 2
> `CardPayment` отвечает за сбор результата платежа, а объект стратегии — только за размер комиссии.

> [!hint]- Подсказка 3
> Если добавление стратегии требует править `CardPayment`, конкретный тип просочился через границу абстракции.

**Рефлексия:** когда словарь функций был бы проще классов Strategy в этой задаче?

## 5. Диагностируйте нарушение подстановки

**Результат:** вы находите нарушение LSP по контракту клиента, а не по сходству предметных названий.

**Предварительно:** [[classes/lsp|предусловия и постусловия]], [[solid/liskovSubstitution/liskovSubstitution|Rectangle/Square и Bird/Penguin]].

В примере `Rectangle`/`Square` клиент выполняет:

```ts
function resizeForBanner(rectangle: Rectangle): number {
  rectangle.setWidth(5);
  rectangle.setHeight(10);
  return rectangle.getArea();
}
```

Составьте диагностический отчёт:

1. Запишите постусловие каждой операции `setWidth` и `setHeight`, которое предполагает клиент базового типа.
2. Пошагово проследите состояние `Rectangle` и `Square` после обоих вызовов.
3. Определите, нарушена ли прозрачная подстановка, даже если программа не бросает исключение.
4. Предложите два редизайна: один с неизменяемыми фигурами, другой с разделёнными интерфейсами возможностей. Не пишите полную реализацию.
5. Добавьте контрактную проверку, которую можно применить к каждому объекту, заявленному как изменяемый прямоугольник.

**Наблюдаемые требования:**

- ожидаемая площадь клиента указана до запуска;
- названа конкретная ослабленная гарантия или изменённое постусловие;
- вывод не опирается на фразу «квадрат является прямоугольником» из геометрии;
- один редизайн исключает проблемный объект из типа, который принимает `resizeForBanner`;
- контрактная проверка падает на несовместимой реализации и проходит на совместимой.

**Ручная и запускаемая проверка:** сначала сравните трассы состояний в таблице, затем вызовите один и тот же тест контракта с `new Rectangle(0, 0)` и `new Square(0, 0)`. Объясните любой различающийся результат как нарушение обещания клиента, а не просто как «другое поведение».

> [!hint]- Подсказка 1
> Контракт setter включает не только изменённое поле, но и то, какие остальные наблюдаемые свойства он сохраняет.

> [!hint]- Подсказка 2
> LSP проверяется относительно клиента: после `setWidth(5)` вызов `setHeight(10)` не должен незаметно отменять первое обещание.

> [!hint]- Подсказка 3
> Общий неизменяемый контракт площади не обязан предоставлять независимое изменение ширины и высоты.

**Рефлексия:** почему отсутствие исключения не доказывает подстановку и какие тесты контракта вы добавили бы для новых подтипов?

## 6. Перенесите State в другую предметную область

**Результат:** вы переносите композицию состояний с экрана телефона на жизненный цикл документа и оцениваете, нужен ли здесь паттерн.

**Предварительно:** [[polymorphism/7.object-composition|объектная композиция]], [[polymorphism/8.state-pattern|State для MobileScreen]].

Спроектируйте `DocumentWorkflow` с состояниями `Draft`, `Review` и `Published`:

- начальное состояние — `Draft`;
- `submit()` переводит `Draft` в `Review`;
- `reject()` переводит `Review` в `Draft`;
- `approve()` переводит `Review` в `Published`;
- `edit(text)` разрешён только в `Draft`;
- недопустимая команда возвращает наблюдаемый результат `"forbidden"`, а не молча меняет состояние;
- `stateName` доступно только для чтения.

Сначала реализуйте вариант с одним явным `stateName` и условными переходами. Затем перенесите поведение в взаимозаменяемые объекты-состояния, сохранив публичный API. Сравните обе версии по числу точек изменения, когда добавляется состояние `Archived` и команда `archive()` из `Published`.

**Наблюдаемые требования:**

- обе версии проходят один набор сценариев клиента;
- объект-состояние получает только необходимый доступ к контексту;
- клиент не проверяет конкретный класс состояния;
- добавление `Archived` не меняет поведение существующих переходов;
- в выводе явно сказано, при каком размере модели условная версия остаётся предпочтительнее.

**Запускаемая проверка:** оформите последовательность как assertions для обеих фабрик `createConditionalWorkflow` и `createStateWorkflow`.

```ts
import assert from "node:assert/strict";

for (const createWorkflow of [
  createConditionalWorkflow,
  createStateWorkflow,
]) {
  const document = createWorkflow();
  assert.equal(document.stateName, "draft");
  assert.equal(document.edit("v1"), "ok");
  assert.equal(document.approve(), "forbidden");
  assert.equal(document.submit(), "ok");
  assert.equal(document.stateName, "review");
  assert.equal(document.edit("v2"), "forbidden");
  assert.equal(document.approve(), "ok");
  assert.equal(document.stateName, "published");
  assert.equal(document.reject(), "forbidden");
  assert.equal(document.archive(), "ok");
  assert.equal(document.stateName, "archived");
}
```

> [!hint]- Подсказка 1
> Сначала запишите таблицу «текущее состояние × команда → результат и следующее состояние».

> [!hint]- Подсказка 2
> Публичные методы контекста могут делегировать одноимённым операциям текущего состояния.

> [!hint]- Подсказка 3
> Состоянию нужен узкий способ запросить переход; передавать наружу все внутренние поля документа необязательно.

**Рефлексия:** что в новой области действительно перенеслось из `MobileScreen` — классы, механизм диспетчеризации или идея локализовать переходы?
