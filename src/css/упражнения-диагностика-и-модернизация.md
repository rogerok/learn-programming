# CSS: диагностика и модернизация

Выполняйте задания после [[эти-css-техники-устарели|source note]] и сохраняйте исходные предсказания. Цель — доказать сохранение layout contract, а не механически заменить старую запись новой.

## 1. Predict: что сохранится после замены

Для каждой пары из заметки — centering, `inset: 0`, logical spacing и Grid вместо column Flexbox — до запуска предскажите:

1. какие границы box останутся прежними;
2. изменится ли участие потомков в normal flow;
3. какое различие проявится при `dir="rtl"`, дополнительном дочернем элементе или изменении размера контейнера.

Затем соберите минимальный HTML/CSS пример для каждой пары и сравните computed styles и bounding boxes в DevTools.

**Наблюдаемый критерий:** сохранена таблица из четырёх строк с предсказанием, измеренным `getBoundingClientRect()` или computed style и отметкой `подтверждено/опровергнуто`. Хотя бы один контекстный input меняется между проверками.

> [!hint]- Подсказка 1
> Сначала сравнивайте геометрию одного элемента при одинаковом viewport, а не внешний вид всей страницы.

> [!hint]- Подсказка 2
> Отдельно фиксируйте positioning scheme и layout mode родителя: короткая запись сама по себе не гарантирует эквивалентность.

> [!hint]- Подсказка 3
> Для logical properties измените writing direction; для Grid/Flex добавьте второго потомка и сравните размещение.

**Рефлексия:** какое предсказание оказалось неверным и какое неявное предположение о layout к этому привело?

## 2. Explain: назвать семантическое условие

Своими словами объясните, при каких условиях каждая модернизация из source note сохраняет intent:

- `top/left/width/height` → `inset`;
- physical `margin`/`padding` → logical properties;
- transform centering → Grid centering;
- column Flexbox → Grid;
- длинный system font stack → `system-ui`.

Для каждого пункта добавьте один counterexample, где замена меняет поведение или product requirement.

**Наблюдаемый критерий:** пять объяснений называют layout intent, необходимое условие и проверяемое последствие нарушения условия. Counterexample задаёт конкретный DOM или environment, а не общую фразу «может сломаться».

> [!hint]- Подсказка 1
> Разделите свойства, которые сокращают ту же модель, и свойства, которые переключают layout algorithm.

> [!hint]- Подсказка 2
> Спросите для каждой пары: совпадают ли containing block, ось, число потомков и требования к browser font?

> [!hint]- Подсказка 3
> Если условие нельзя проверить через computed style, geometry или поведение при изменённом input, уточните его.

**Рефлексия:** какие из пяти изменений являются синтаксическим упрощением, а какие — новым архитектурным решением layout?

## 3. Diagnose: остановить слепой codemod

Рассмотрите предполагаемый codemod:

```diff
-.panel { display: flex; flex-direction: column; gap: 1rem; }
+.panel { display: grid; gap: 1rem; }

-.badge { position: absolute; top: 50%; left: 50%; transform: translate(-50%, -50%); }
+.badge-parent { display: grid; place-items: center; }
```

Не исправляя код, найдите минимальный DOM и CSS context, в котором каждый change нарушает исходный contract. Сначала запишите ожидаемый failure, затем воспроизведите его в браузере и локализуйте причину до конкретного layout rule.

**Наблюдаемый критерий:** для каждой замены есть минимальная reproduction, ожидаемое и фактическое наблюдение, затронутый invariant и условие, при котором codemod допустим. Диагноз не опирается только на screenshot: приложено значение geometry или computed style.

> [!hint]- Подсказка 1
> Добавьте поведение, которое зависит не только от вертикального визуального расположения одного потомка.

> [!hint]- Подсказка 2
> Для `.badge` проверьте containing block, overlap и участие элемента в flow до и после change.

> [!hint]- Подсказка 3
> Для `.panel` сравните оси, sizing и выравнивание нескольких потомков; ищите правило, которое отличается у Grid и Flexbox.

**Рефлексия:** какой precondition вы добавили бы в автоматизацию, а какой change оставили бы только для manual review?

## 4. Transfer: подготовить проверяемую modernization

Возьмите реальный компонент с overlay и внутренней вертикальной группой. Не меняя HTML и visual contract, предложите modernization plan, используя только те приёмы из source note, чью эквивалентность вы можете обосновать.

До изменения зафиксируйте:

1. viewport и writing directions для проверки;
2. bounding boxes overlay и ключевых потомков;
3. keyboard focus order и scroll behavior;
4. fallback или причину, почему он не нужен.

После изменения повторите те же наблюдения. Полный итоговый CSS в заметку не переносите: сохраните только patch у себя и отчёт о сравнении.

**Наблюдаемый критерий:** test matrix содержит минимум два viewport, `ltr` и `rtl`, состояние с длинным content и состояние с keyboard focus. Для каждой строки записан ожидаемый invariant и фактический результат; любое намеренное отличие объяснено как изменение requirement.

> [!hint]- Подсказка 1
> Начните с сокращений внутри той же positioning или spacing model, прежде чем менять layout mode.

> [!hint]- Подсказка 2
> Проверяйте overflow и containing block отдельно от центрирования видимого content.

> [!hint]- Подсказка 3
> Если Grid заменяет Flexbox, сформулируйте, почему двумерный Grid algorithm сохраняет именно contract этого компонента, а не просто похожий screenshot.

**Рефлексия:** какое доказательство сильнее всего поддерживает modernization: уменьшение CSS, совпадение computed styles, geometry across inputs или отсутствие regression в interaction — и почему?
