# Практика: функции и switch

Для каждого задания создайте отдельный `.go`-файл. Сначала запишите ожидаемый stdout, затем выполните `go run <имя-файла>.go`. Готовых решений нет: критерий завершения — совпадение прогноза с наблюдением и объяснение поведения.

## 1. Предсказать и объяснить returns

**Результат:** отличить zero value, naked return и explicit return по наблюдаемому поведению.

**Пререквизиты:** [[functions|Named и explicit returns]].

```go
package main

import "fmt"

func coords() (x, y int) {
	x = 2
	return
}

func override() (x, y int) {
	x = 2
	y = 3
	return 5, 6
}

func main() {
	fmt.Println(coords())
	fmt.Println(override())
}
```

Не запускайте программу, пока не запишете обе строки stdout и происхождение каждого числа.

**Приёмка:**

- прогноз содержит ровно две строки и четыре возвращаемых значения;
- `go run` завершается с кодом `0`, stdout совпадает с прогнозом строка в строку;
- объяснение указывает, какое значение осталось zero value, что вернул naked return и почему explicit return не обязан совпадать с текущими named values.

**Контрольная точка:** после первого запуска присвойте `y` значение перед naked return в `coords`, снова предскажите обе строки и только затем повторите запуск.

> [!hint]- Подсказка 1
> Каждый named return parameter создаётся при входе в функцию и получает zero value своего типа.

> [!hint]- Подсказка 2
> `return` без аргументов использует текущие `x` и `y`; `return 5, 6` возвращает выражения после `return`.

**Рефлексия:** в какой из двух функций naked return легче прочитать через полгода? Как длина функции могла бы изменить ваш ответ?

## 2. Модифицировать и диагностировать fallthrough

**Результат:** найти ветку, нарушающую новый контракт, и исправить её без нежелательного перехода в следующий `case`.

**Пререквизиты:** [[switch|Switch, неявный break и fallthrough]].

```go
package main

import "fmt"

func creator(os string) string {
	var name string

	switch os {
	case "linux":
		name = "Linus Torvalds"
	case "macOS":
		fallthrough
	case "mac":
		name = "A Steve"
	default:
		name = "Unknown"
	}

	return name
}

func main() {
	fmt.Println(creator("linux"))
	fmt.Println(creator("macOS"))
	fmt.Println(creator("mac"))
	fmt.Println(creator("plan9"))
}
```

Новый контракт требует: `macOS` возвращает `Apple`, `mac` — `A Steve`; результаты `linux` и неизвестной строки остаются прежними. Сначала диагностируйте фактический путь `macOS`, затем измените `switch`.

**Приёмка:**

- до изменения записаны четыре строки фактического stdout и указаны выполненные `case` для `macOS`;
- после изменения все четыре входа соответствуют контракту;
- в итоговом варианте нет `fallthrough`, потому что соседние ветки теперь имеют разные результаты;
- `go run` завершается с кодом `0`, а число строк stdout не изменилось.

**Контрольная точка:** добавьте временный `fmt.Println` внутрь двух соседних веток, чтобы увидеть путь `macOS`; удалите диагностический вывод перед итоговой проверкой.

> [!hint]- Подсказка 1
> В Go обычный `case` завершается неявно. Дополнительное ключевое слово нужно только для намеренного выполнения тела следующей ветки.

> [!hint]- Подсказка 2
> Если результаты веток различаются, дайте каждой ветке собственное присваивание и позвольте неявному `break` завершить выбор.

**Рефлексия:** когда `fallthrough` делает намерение яснее, а когда скрывает ошибку? Какой review-вопрос поможет различить эти случаи?

## 3. Реализовать и перенести поведение

**Результат:** соединить named returns и `switch` в небольшой функции с наблюдаемым контрактом и безопасным граничным случаем.

**Пререквизиты:** выполненные задания 1–2.

Начальная программа уже корректно поддерживает умножение и запускается:

```go
package main

import "fmt"

func calculate(op string, a, b int) (value int, ok bool) {
	switch op {
	case "mul":
		return a * b, true
	default:
		return 0, false
	}
}

func main() {
	fmt.Println(calculate("mul", 3, 4))
	fmt.Println(calculate("div", 9, 3))
	fmt.Println(calculate("div", 9, 0))
	fmt.Println(calculate("sub", 9, 3))
}
```

Расширьте `calculate`: операция `div` выполняет целочисленное деление, но при нулевом делителе возвращает zero value результата и `false`. Неизвестная операция также возвращает zero value и `false`.

**Приёмка:**

| Вызов | Наблюдаемый контракт |
|---|---|
| `calculate("mul", 3, 4)` | `12, true` |
| `calculate("div", 9, 3)` | `3, true` |
| `calculate("div", 9, 0)` | `0, false`, без panic |
| `calculate("sub", 9, 3)` | `0, false` |

- `go run` завершается с кодом `0` и печатает четыре строки в том же порядке;
- деление не вычисляется до проверки `b`;
- сигнатура с named returns сохранена, а выбор naked или explicit returns кратко обоснован;
- добавлен собственный перенос: ещё одна поддерживаемая операция и минимум один её граничный вход, не меняющие поведение неизвестных операций.

**Контрольная точка:** сначала реализуйте успешный `div`, запустите сценарий с ненулевым делителем, затем добавьте нулевой граничный случай и убедитесь, что программа не падает.

> [!hint]- Подсказка 1
> Внутри `case "div"` проверка делителя должна предшествовать выражению `a / b`.

> [!hint]- Подсказка 2
> Для неуспеха достаточно пары, совместимой с `(value int, ok bool)`. Решите, улучшает ли здесь naked return читаемость, или явная пара лучше показывает контракт.

**Рефлексия:** что именно сообщает `ok`, чего нельзя надёжно вывести только из `value`? Как изменится API, если вызывающему коду понадобится различать неизвестную операцию и деление на ноль?
