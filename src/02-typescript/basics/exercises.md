# Практика: фундамент системы типов TypeScript

Задания идут по траектории **predict → explain → modify → implement → diagnose → transfer**. Работайте в отдельном `fundamentals.ts` и проверяйте именно поведение компилятора и программы, а не текст конспекта.

Базовая команда:

```bash
tsc --strict --noEmit --noUncheckedIndexedAccess fundamentals.ts
```

Для намеренно ошибочной строки после прогноза используйте `// @ts-expect-error`: команда должна завершиться без ошибок, а исчезновение ожидаемой ошибки само станет ошибкой `Unused '@ts-expect-error' directive`. Не используйте `any`, `as` и non-null assertion (`!`), если задание прямо этого не требует.

## 1. Predict: множества и присваиваемость

**Результат:** до запуска компилятора предсказать направление присваиваемости для literals, object types и `never`.

**Предпосылки:** [[code-basic/type-as-set|Типы как множества]], [[code-basic/assignability|Присваиваемость]], [[code-basic/never|never]].

Скопируйте код и сначала пометьте каждую строку присваивания как «примет» или «отклонит», не запуская `tsc`:

```ts
type Point = { x: number };

const detailed = { x: 1, y: 2 };
const fromVariable: Point = detailed;
const fromLiteral: Point = { x: 1, y: 2 };

let text: string = "ok";
const literal: "ok" = "ok";
text = literal;
const sameLiteral: "ok" = text;

const bottom: never = literal;
```

**Наблюдаемая приёмка:**

- прогноз записан до первого запуска;
- после запуска каждая отклоняемая строка отмечена `@ts-expect-error`, и базовая команда завершается с кодом `0`;
- для каждого несовпадения прогноза указано, какое множество значений шире;
- отдельно объяснено, почему результат для object literal может отличаться от результата для переменной.

**Проверка:** временно удалите один `@ts-expect-error`: `tsc` должен вернуть ошибку именно на соответствующей строке.

> [!hint]- Подсказка 1
> Значение узкого типа можно использовать там, где ожидается более широкое множество значений.

> [!hint]- Подсказка 2
> Для свежего object literal действует дополнительный Excess Property Check; это не новое правило подтипизации.

**Рефлексия:** какая из ошибок была следствием присваиваемости, а какая — отдельной эвристикой компилятора?

## 2. Explain: структурная совместимость

**Результат:** объяснить совместимость через требуемые поля и подтвердить объяснение двумя наблюдаемыми compile-time случаями.

**Предпосылки:** задание 1, [[code-basic/structural-typing|Структурная типизация]].

Даны два независимо названных типа:

```ts
type RequestUser = { id: string; name: string };
type CachedUser = { id: string; name: string; cachedAt: Date };

declare function showUser(user: RequestUser): string;
const cached: CachedUser = {
  id: "u-1",
  name: "Ada",
  cachedAt: new Date(0),
};
```

Добавьте только вызовы и короткое объяснение, не меняя объявления типов.

**Наблюдаемая приёмка:**

- вызов с `cached` компилируется;
- прямой object literal с теми же тремя полями отклоняется и защищён `@ts-expect-error`;
- объяснение называет требуемые поля, дополнительные поля и freshness literal, а не совпадение имён типов;
- базовая команда завершается с кодом `0`.

**Ручной checkpoint:** переименуйте `CachedUser`, не меняя его структуру: результат проверки не должен измениться.

> [!hint]- Подсказка 1
> Сравните не имена aliases, а минимальный контракт параметра `showUser`.

> [!hint]- Подсказка 2
> Сначала передайте существующую переменную, затем тот же объект запишите прямо в аргументе вызова.

**Рефлексия:** какую опечатку ловит Excess Property Check и почему нельзя считать его проверкой «точного объекта» во всех контекстах?

## 3. Modify: control-flow narrowing

**Результат:** исправить функцию через runtime-проверки так, чтобы каждая операция выполнялась только над подходящим вариантом union.

**Предпосылки:** [[code-basic/narrowing|Сужение типов]], [[code-basic/unknown|unknown]].

Стартовый код намеренно не компилируется:

```ts
function describe(value: string | number | null): string {
  return value.trim();
}
```

Измените только тело `describe`. Запрещены `as`, `any`, `!` и изменение сигнатуры.

**Наблюдаемая приёмка:**

- `describe("  hi  ") === "hi"`;
- `describe(3.14) === "3.1"`;
- `describe(null) === "нет данных"`;
- базовая команда завершается с кодом `0`, runtime-проверки завершаются без исключений.

**Проверка:** добавьте тесты через `console.assert`, затем выполните скомпилированный файл или доступным TypeScript runner.

> [!hint]- Подсказка 1
> Сначала исключите `null` сравнением, которое реально выполнится в JavaScript.

> [!hint]- Подсказка 2
> `typeof` разделяет оставшиеся `string` и `number`; после раннего `return` TypeScript помнит исключённый вариант.

**Рефлексия:** какие операции в каждой ветке стали доступны и какое множество значений осталось после каждой проверки?

## 4. Implement: связь объекта и ключа

**Результат:** реализовать generic-функцию, сохраняющую зависимость между объектом, допустимым ключом и типом результата.

**Предпосылки:** [[code-basic/generics|Дженерики]], задания 1–3.

Реализуйте `getProperty` без overloads, `any` и assertions. Проверочный call site:

```ts
const account = { id: 7, owner: "Ada", active: true };

const id: number = getProperty(account, "id");
const owner: string = getProperty(account, "owner");
const active: boolean = getProperty(account, "active");

// @ts-expect-error — такого ключа нет
getProperty(account, "email");
```

**Наблюдаемая приёмка:**

- все три корректных присваивания сохраняют разные типы результата;
- неизвестный ключ отклоняется компилятором;
- реализация состоит из одной сигнатуры и работает для других object types;
- базовая команда завершается с кодом `0`.

**Ручной checkpoint:** добавьте объект `{ createdAt: Date }`; результат для `"createdAt"` должен выводиться как `Date` без явного type argument.

> [!hint]- Подсказка 1
> Нужны два параметра типа: один для объекта, второй для его ключа.

> [!hint]- Подсказка 2
> Ограничьте ключ через `keyof`, а тип результата получите indexed access типом.

**Рефлексия:** какая связь потерялась бы, если вернуть union всех типов свойств объекта?

## 5. Diagnose: ковариантность мутабельного массива

**Результат:** воспроизвести runtime-ошибку в программе, принятой строгим компилятором, назвать причину и убрать опасную мутацию контрактом типов.

**Предпосылки:** [[code-basic/variability|Вариантность]], [[code-basic/readonly-array|Readonly arrays]], [[../unsound/unsound|Небезопасность TypeScript]].

```ts
interface Animal {
  kind: string;
}

interface Dog extends Animal {
  bark(): void;
}

const dogs: Dog[] = [{ kind: "dog", bark: () => console.log("woof") }];
const animals: Animal[] = dogs;
animals.push({ kind: "cat" });
dogs[1].bark();
```

Сначала зафиксируйте результат `tsc`, затем запустите JavaScript и зафиксируйте исключение. После этого измените контракт так, чтобы чтение оставалось допустимым, а мутация через более широкий тип отклонялась.

**Наблюдаемая приёмка:**

- исходный вариант компилируется с `--strict`, но падает в runtime;
- объяснение называет aliasing, ковариантность `Dog[] → Animal[]` и запись `Animal` через широкий alias;
- в исправленном варианте попытка `push` отмечена `@ts-expect-error`, базовая команда завершается с кодом `0`, runtime не падает;
- исходный `dogs` не получает значение без метода `bark`.

**Проверка:** уберите `@ts-expect-error` с запрещённой мутации — компилятор должен сообщить, что операция недоступна.

> [!hint]- Подсказка 1
> Ошибка возникает не при чтении `Animal`, а при записи через alias, у которого более широкий элементный тип.

> [!hint]- Подсказка 2
> Выразите контракт «только чтение» в типе ссылки, через которую доступен широкий взгляд на массив.

**Рефлексия:** почему `strictFunctionTypes` не делает мутабельные массивы инвариантными и где ещё aliasing ломает локальное рассуждение о типе?

## 6. Transfer: недоверенное событие на границе системы

**Результат:** перенести модель множеств, narrowing и exhaustive check на обработку данных типа `unknown`.

**Предпосылки:** задания 1–5, [[code-basic/narrowing|Сужение типов]], [[code-basic/never|never]].

Опишите union `DomainEvent` с вариантами:

- `{ type: "created"; id: string }`;
- `{ type: "failed"; id: string; reason: string }`.

Реализуйте две функции без `as`, `any` и non-null assertion:

- `parseEvent(input: unknown): DomainEvent | undefined` проверяет runtime-форму внешних данных;
- `summarize(event: DomainEvent): string` обрабатывает union исчерпывающе.

**Наблюдаемая приёмка:**

- корректные объекты обоих вариантов проходят parsing;
- неизвестный `type`, отсутствующее поле, поле неверного типа, `null` и primitive возвращают `undefined` без исключения;
- `summarize` возвращает строку, содержащую `id`, а для `failed` также `reason`;
- базовая команда завершается с кодом `0`, runtime-таблица минимум из семи случаев проходит;
- после временного добавления варианта `{ type: "cancelled"; id: string }` компилятор требует обновить исчерпывающую обработку.

**Проверка:** составьте таблицу `{ input, expected }` и прогоните её циклом; compile-time проверку нового варианта выполните отдельно и затем отмените временное изменение.

> [!hint]- Подсказка 1
> Начните с исключения `null` и не-`object`; затем проверяйте наличие полей и тип каждого значения.

> [!hint]- Подсказка 2
> Маленькие type guards для общих полей уменьшают дублирование, но их тела остаются вашей runtime-ответственностью.

> [!hint]- Подсказка 3
> После всех `case` оставшееся значение должно присваиваться `never`; это и есть наблюдаемый сигнал неполной обработки.

**Рефлексия:** где заканчивается гарантия TypeScript и какое runtime-доказательство превращает `unknown` в доверенный `DomainEvent`?
