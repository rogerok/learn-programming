# Трассировка и проверка mental model V8

Сначала запишите гипотезу, затем получите наблюдение. Адреса объектов и служебные строки зависят от версии Node.js, поэтому проверяйте названия `ElementsKind` и совпадение Map, а не конкретные адреса или число строк вывода.

## 1. Предсказать и объяснить переходы ElementsKind

**Результат:** построить цепочку внутренних представлений массива и проверить её через `%DebugPrint()`.

**Пререквизиты:** [[v8-engine-internals#5. Массивы: ElementsKind|ElementsKind и необратимые переходы]], [[v8-engine-internals#7. Инструменты для наблюдения за V8|инструменты наблюдения]].

Сохраните программу в отдельный файл:

```js
const values = [1, 2, 3];
console.log("A: integers");
%DebugPrint(values);

values.push(4.5);
console.log("B: double");
%DebugPrint(values);

values.push("5");
console.log("C: mixed");
%DebugPrint(values);

delete values[1];
console.log("D: hole");
%DebugPrint(values);
```

До запуска для точек A–D запишите ожидаемый `ElementsKind` и событие, вызвавшее переход. Затем выполните `node --allow-natives-syntax <имя-файла>.js` и найдите строки `elements kind` рядом с метками.

**Приёмка:**

- таблица содержит четыре последовательных состояния без пропусков;
- каждое состояние связано с конкретной операцией `push` или `delete`;
- наблюдаемые названия `ElementsKind` сопоставлены с прогнозом;
- если прогноз неверен, исправлена mental model, а не скопирован весь нестабильный служебный вывод.

**Контрольная точка:** после точки D присвойте число удалённому индексу и снова вызовите `%DebugPrint()`; объясните, почему заполнение дыры не обязано возвращать прежний packed-kind.

> [!hint]- Подсказка 1
> Сначала различайте две независимые оси: тип элементов (`SMI` → `DOUBLE` → общий) и наличие дыр (`PACKED` → `HOLEY`).

> [!hint]- Подсказка 2
> Двигайтесь по решётке переходов только в сторону менее специализированного представления; обратная стрелка потребовала бы нового массива.

**Рефлексия:** какая строка пользовательского кода вызвала самый большой переход в представлении и почему результат функции при этом мог остаться прежним?

## 2. Модифицировать и диагностировать формы объектов

**Результат:** обнаружить разные Hidden Classes у семантически одинаковых объектов и стабилизировать порядок инициализации.

**Пререквизиты:** [[jit-compilation#Шаг 6 — Hidden Classes и Inline Caches|Hidden Classes и Inline Caches]], [[v8-engine-internals#4. Объекты: Hidden Classes|Maps объектов]].

```js
function makePoint(x, y, reversed) {
  if (reversed) {
    return { y, x };
  }
  return { x, y };
}

const first = makePoint(1, 2, false);
const second = makePoint(3, 4, true);

console.log(first.x + second.x);
%DebugPrint(first);
%DebugPrint(second);
```

Предскажите stdout и сравните строки `map:` двух объектов после запуска с `--allow-natives-syntax`. Затем измените фабрику так, чтобы свойства создавались в одном порядке для обоих путей, сохранив значения `x` и `y`.

**Приёмка:**

- до изменения записаны ожидаемый пользовательский результат и гипотеза о совпадении Map;
- наблюдение до изменения сравнивает именно Map, а не адреса самих объектов;
- после изменения пользовательский stdout не меняется, а строки Map у двух объектов совпадают;
- объяснение связывает различие с порядком добавления свойств, а не с разными числовыми значениями.

**Контрольная точка:** запустите один и тот же файл до и после изменения и сохраните только три устойчивых факта: stdout, «Map совпадает/не совпадает» и порядок полей.

> [!hint]- Подсказка 1
> Hidden Class описывает форму: имена свойств и порядок их появления. Значения `1` и `3` сами по себе не требуют разных форм.

> [!hint]- Подсказка 2
> Найдите одну точку создания объекта, через которую проходят обе ветки. Ветвление может выбирать значения, не меняя порядок объявления полей.

**Рефлексия:** почему два объекта с одинаковым набором ключей могут давать полиморфный доступ? Какое правило вы перенесёте в review фабрик и конструкторов?

## 3. Реализовать и перенести модель на числовую коллекцию

**Результат:** выбрать представление для новой задачи и обосновать его через инварианты данных и наблюдение V8.

**Пререквизиты:** выполненное задание 1; рекомендация о `TypedArray` в [[v8-engine-internals#5.3 Практические примеры|практических примерах ElementsKind]].

Исходный вариант запускается, но создаёт смешанный обычный массив:

```js
function collect(values) {
  return values.map((value) => value);
}

const result = collect([1, 2.5, "3", Number.NaN, 4]);
console.log(result);
```

Реализуйте `collectNumeric(values)`, возвращающую `Float64Array` только из конечных значений с JavaScript-типом `number`. Строка `"3"` не должна неявно преобразовываться. Добавьте наблюдаемые проверки результата и при необходимости `%DebugPrint()`.

**Приёмка:**

- результат является `Float64Array`, содержит только допустимые входные числа в исходном порядке и не содержит дыр;
- `Number.NaN`, бесконечности и строки исключены по явно сформулированному правилу;
- исходный массив не изменяется;
- запускаемый сценарий проверяет тип результата, длину, порядок и граничные входы: пустой массив и массив без допустимых значений;
- выбор `Float64Array` объяснён требованиями новой задачи, а не утверждением, что он всегда быстрее обычного массива.

**Контрольная точка:** отдельно запустите сценарии со значениями `2.5`, `"3"` и `Number.NaN`; для каждого сначала запишите, проходит ли оно фильтр и почему.

> [!hint]- Подсказка 1
> Предикат должен проверять и JavaScript-тип, и конечность числа. Сначала соберите допустимые значения без преобразования строк.

> [!hint]- Подсказка 2
> У `Float64Array` фиксированная длина. Можно сначала определить допустимые элементы, а затем один раз создать typed array нужного размера.
