# Быстрая практика этапа 5 — Effect coordination

Набор закрепляет четыре границы отдельно от booking domain. Выполняйте упражнения по порядку и не открывайте реализацию `makeBookingProcessor` до первой попытки.

Запуск всего набора:

```bash
npm run practice:5
```

Запуск одного упражнения:

```bash
npm run practice:5 -- -t "Queue + Deferred"
```

Рабочий файл: `src/practice/coordination.ts`. Проверки находятся в `checks/practice-5-coordination.test.ts`. Starter намеренно компилируется, но каждая функция завершается ошибкой до вашей реализации.

## Упражнение 1: связать producer с его результатом

**Результат обучения:** реализовать request/reply boundary через общую `Queue` и отдельный `Deferred` каждого producer.

**Перед кодом:** для двух конкурентных producers нарисуйте два разных `reply` и укажите, кто создаёт и кто завершает каждый из них.

**Задание:** реализуйте `submitWork` и `processOne`.

- `submitWork` передаёт `input` consumer-у и возвращает преобразованный результат.
- `processOne` обрабатывает ровно один элемент.
- Результат одного producer не должен попасть другому.
- Не создавайте отдельную очередь на каждый request.

**Критерий проверки:** два конкурентных request получают `[20, 70]` от одного worker без timeout.

> [!tip]- Подсказка 1: responsibilities
> Producer владеет reply channel; consumer владеет его завершением.

> [!tip]- Подсказка 2: порядок producer
> Сначала создайте reply, затем поместите `{ input, reply }` в queue, затем ожидайте reply.

> [!tip]- Подсказка 3: порядок consumer
> Consumer забирает один `WorkItem`, применяет `transform` и завершает reply вычисленным значением.

## Упражнение 2: отделить бесконечные workers от setup

**Результат обучения:** запустить заданное число фоновых workers так, чтобы setup завершился, а fibers остановились вместе со scope.

**Перед кодом:** предскажите результат простого `yield* worker`, если `worker` имеет тип `Effect<never>`.

**Задание:** реализуйте `startWorkers(count, worker)`.

- Должны стартовать ровно `count` копий одного effect.
- `startWorkers` должен вернуть управление, хотя workers бесконечны.
- После закрытия scope все workers должны быть прерваны.
- Не используйте daemon fibers.

**Критерий проверки:** внутри scope активны три workers; после его закрытия активных workers нет и три finalizer-а выполнены.

> [!tip]- Подсказка 1: lifetime
> Запуск effect и ожидание его результата — разные операции.

> [!tip]- Подсказка 2: ownership
> Нужна операция fork, которая регистрирует child fiber в текущем `Scope`.

## Упражнение 3: ограничить одну внешнюю операцию

**Результат обучения:** применить общий `Semaphore` так, чтобы одна операция занимала один permit, а все inputs обрабатывались конкурентно до заданного лимита.

**Перед кодом:** вычислите максимальную concurrency для semaphore с двумя permits, если одна операция запрашивает два permits.

**Задание:** реализуйте `runLimited(inputs, concurrency, operation)`.

- Создайте один общий semaphore для всего запуска.
- Запустите обработку inputs конкурентно.
- Ограничьте permit-ом только `operation(input)`.
- Одна операция имеет вес один permit.
- Не заменяйте semaphore последовательным `forEach`.

**Критерий проверки:** все пять inputs обработаны, а наблюдаемый максимум одновременных операций равен двум.

> [!tip]- Подсказка 1: две настройки
> Общее число permits задаётся при создании semaphore; вес одной операции задаётся при её запуске.

> [!tip]- Подсказка 2: скрытая сериализация
> Если внешний обход inputs последовательный, semaphore не сможет показать concurrency больше одного.

## Упражнение 4: отделить broadcast от callback

**Результат обучения:** реализовать scoped broadcaster, в котором каждый subscriber читает личную subscription queue в отдельной fiber.

**Перед кодом:** объясните, почему бесконечный цикл непосредственно внутри `subscribe` не позволит регистрации завершиться.

**Задание:** реализуйте `makeBroadcaster(capacity)`.

- `publish(message)` отправляет сообщение через один `PubSub`.
- Каждый `subscribe(callback)` создаёт отдельную subscription queue.
- Callback выполняется в отдельной consumer fiber с циклом `take → callback`.
- `subscribe` возвращает управление сразу после запуска consumer.
- Subscription и consumer принадлежат scope broadcaster-а.
- После закрытия scope callbacks больше не вызываются.

**Критерий проверки:** два subscribers независимо получают `held → confirmed → rejected` в одинаковом порядке; публикация после закрытия scope не вызывает callbacks.

> [!tip]- Подсказка 1: две lifetime
> Короткий effect регистрации создаёт и запускает отдельный бесконечный consumer effect.

> [!tip]- Подсказка 2: один владелец
> Захватите scope broadcaster-а; в него должны быть extended subscription и forked consumer.
