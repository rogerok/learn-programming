# Планировщик асинхронных задач

Этот проект — управляемая практика по проектированию небольшой очереди поверх `Promise`. Начальная версия уже компилируется, хранит задачи и выполняет их. Она намеренно не гарантирует порядок результатов, не обновляет состояние, прерывается на первой ошибке, игнорирует `concurrency` и видит только задачи, существовавшие в начале запуска.

## Цели обучения

После четырёх этапов вы сможете:

- отличать порядок запуска, завершения и выдачи результатов `Promise`;
- явно моделировать переходы состояния очереди;
- сохранять ошибку как результат конкретной задачи, не теряя остальные задачи;
- ограничивать число одновременно выполняемых задач без пакетной обработки;
- продолжать обработку, когда новая задача добавлена во время `run()`.

## Как устроен проект

- `src/scheduler.ts` — единственный файл, который нужно изменять;
- `src/index.ts` — небольшой запускаемый пример начальной версии;
- `checks/milestone-*.test.ts` — наблюдаемые требования этапов;
- `checks/starter.test.ts` — зелёная проверка возможностей начальной версии;
- `npm run check:N` — накопительная проверка: этап `N` включает все предыдущие;
- `npm test` — starter-safe тест, который проходит до выполнения этапов;
- `npm run build` — строгая проверка TypeScript;
- `npm run lint` — локальная статическая проверка исходников и проверок;
- `npm run smoke` — запуск примера без тестового раннера.

Публичный контракт уже задан типами `Task`, `TaskOutcome`, `TaskSnapshot` и классом `TaskScheduler`. Не меняйте имена и форму этих типов: проверки рассматривают их как интерфейс проекта.

## Рабочий цикл

1. Установите зависимости командой `npm install` из этой директории.
2. Выполните `npm run lint`, `npm run build`, `npm test` и `npm run smoke`: начальная версия должна пройти базовые проверки и реально запускать задачи.
3. Перед этапом прочитайте только его условие и ручную контрольную точку.
4. Запустите соответствующую накопительную проверку, например `npm run check:2`.
5. Внесите минимальное изменение в `src/scheduler.ts` и повторите проверку.
6. Если застряли, открывайте подсказки по одной. Эталон в конце нужен для сравнения после собственной реализации, а не для первого шага.

Красный результат проверки до реализации этапа ожидаем. Важен текст падения: он должен указывать на отсутствующее поведение, а не на импорт, конфигурацию или запуск среды.

## Этап 1. Порядок результатов

Две задачи могут завершиться не в том порядке, в котором были добавлены. Метод `run()` всё равно должен вернуть массив результатов в порядке очереди. Сами задачи не нужно искусственно делать последовательными: при `concurrency: 2` быстрая задача вправе закончиться первой.

**Готово, когда:** `npm run check:1` проходит, а журнал завершения в проверке остаётся обратным порядку результата.

### Ручная контрольная точка

Временно добавьте в `src/index.ts` две задачи с управляемыми `Promise`: вторая должна разрешить `Promise` первой. Убедитесь, что побочные эффекты фиксируют фактический порядок завершения, а `run()` выдаёт порядок добавления. Затем отмените это временное изменение.

<details>
<summary>Подсказка 1 — где теряется порядок</summary>

`push` внутри асинхронного обработчика отражает момент завершения. Индекс исходной записи уже содержит нужный стабильный порядок.

</details>

<details>
<summary>Подсказка 2 — подходящий примитив</summary>

`Promise.all` сохраняет порядок входного массива в возвращаемом массиве, даже если отдельные `Promise` завершаются иначе.

</details>

<details>
<summary>Подсказка 3 — форма изменения</summary>

Пусть функция, переданная в `map`, возвращает `TaskOutcome`, а не изменяет общий массив через `push`. Результат `await Promise.all(...)` и будет значением `run()`.

</details>

## Этап 2. Состояние очереди

Каждая запись проходит переходы `queued → running → fulfilled`. При `concurrency: 1` вторая запись обязана оставаться `queued`, пока первая ждёт разрешения своего `Promise`. `snapshot()` возвращает снимок значений, а не внутренние изменяемые записи.

На этом этапе начните действительно учитывать `concurrency`. Полная проверка ограничения параллелизма появится на этапе 4, но последовательный запуск нужен уже сейчас, чтобы состояние очереди было наблюдаемым.

**Готово, когда:** `npm run check:2` проходит; снимок во время заблокированной первой задачи показывает `running` только у неё.

### Ручная контрольная точка

Поставьте breakpoint или временный `console.log` непосредственно перед и после `await execute()`. Для двух задач и `concurrency: 1` проверьте последовательность состояний. Уберите диагностический вывод после наблюдения.

<details>
<summary>Подсказка 1 — момент перехода</summary>

Устанавливайте `running` непосредственно перед вызовом задачи, а `fulfilled` только после успешного `await`. Если изменить состояние после вызова, синхронное исключение оставит неверный снимок.

</details>

<details>
<summary>Подсказка 2 — последовательная очередь</summary>

Для первого варианта достаточно курсора по массиву и одного асинхронного worker. Worker берёт запись, обновляет состояние, ждёт результат и переходит к следующему индексу.

</details>

<details>
<summary>Подсказка 3 — подготовка к общему решению</summary>

Сделайте число worker равным `concurrency`. Общий курсор можно увеличивать синхронно до первого `await`: JavaScript выполнит этот участок целиком, поэтому два worker не возьмут одну запись.

</details>

## Этап 3. Ошибка как результат задачи

Ошибка одной задачи не должна отклонять весь `run()` и останавливать очередь. Для ошибочной записи верните вариант `{ id, status: "rejected", reason }`, переведите её состояние в `rejected`, затем продолжите выполнение следующих записей. Не заменяйте исходную ошибку строкой и не скрывайте её.

**Готово, когда:** `npm run check:3` проходит; после синхронного исключения первая запись отклонена, вторая выполнена, а исходный объект `Error` доступен в результате.

### Ручная контрольная точка

Добавьте между двумя успешными задачами задачу, которая синхронно бросает `Error`. Вызов `run()` должен разрешиться массивом из трёх результатов, а снимок — содержать `rejected` только у средней записи. Удалите временный сценарий после проверки.

<details>
<summary>Подсказка 1 — граница обработки</summary>

`try/catch` должен окружать `await record.execute()` внутри worker. Обёртка только вокруг общего `Promise.all` уже не знает, какая запись породила ошибку, и не позволяет worker продолжить очередь.

</details>

<details>
<summary>Подсказка 2 — синхронные и асинхронные ошибки</summary>

Один и тот же `try/catch` вокруг `await` перехватит и синхронный `throw`, и отклонение возвращённого `Promise`.

</details>

<details>
<summary>Подсказка 3 — стабильная выдача</summary>

Сохраните `TaskOutcome` рядом с соответствующей записью. После завершения worker сформируйте ответ проходом по массиву записей — так ошибка не нарушит порядок результатов.

</details>

## Этап 4. Ограниченная параллельность и живая очередь

Теперь параметр `concurrency` должен быть настоящей верхней границей одновременно активных задач. Не запускайте всю очередь через один `Promise.all` и не обрабатывайте её фиксированными пакетами: оба подхода мешают живой очереди.

Задача вправе вызвать `scheduler.add(...)` во время собственного выполнения. Новая запись должна быть замечена текущим запуском, выполнена с тем же ограничением и попасть в итоговый массив в порядке добавления.

**Готово, когда:** `npm run check:4` проходит; максимум активных задач равен двум, третья не стартует до освобождения worker, а поздняя задача присутствует в событиях и результатах.

### Ручная контрольная точка

Запустите три задачи с `concurrency: 2`, ведите счётчик активных задач и заблокируйте первые две управляемым `Promise`. До освобождения счётчик не должен превышать два. Из одной задачи добавьте четвёртую и убедитесь, что она выполнена до разрешения `run()`.

<details>
<summary>Подсказка 1 — почему не нужен снимок массива</summary>

Копия `const initialBatch = [...records]` навсегда фиксирует длину очереди. Worker должен каждый раз читать запись из исходного `records` по текущему индексу.

</details>

<details>
<summary>Подсказка 2 — ограничение без семафора</summary>

Запустите ровно `concurrency` одинаковых worker через `Promise.all`. Каждый worker последовательно берёт одну запись за другой; число ожидающих `execute()` тогда физически не может превысить число worker.

</details>

<details>
<summary>Подсказка 3 — поздняя запись</summary>

Не сохраняйте длину массива перед циклом. Условие worker должно читать `records[cursor]` на каждой итерации. Задача, добавленная до завершения активного worker, окажется доступна при его следующем проходе.

</details>

<details>
<summary>Эталонная реализация src/scheduler.ts — открывать после собственной версии</summary>

```ts
export type TaskState = "queued" | "running" | "fulfilled" | "rejected";

export type TaskOutcome<T = unknown> =
  | { id: string; status: "fulfilled"; value: T }
  | { id: string; status: "rejected"; reason: unknown };

export interface TaskSnapshot {
  id: string;
  state: TaskState;
}

export type Task<T = unknown> = () => T | Promise<T>;

interface TaskRecord {
  id: string;
  execute: Task;
  state: TaskState;
  outcome?: TaskOutcome;
}

export class TaskScheduler {
  private readonly records: TaskRecord[] = [];
  private readonly concurrency: number;

  constructor(options: { concurrency: number }) {
    if (!Number.isInteger(options.concurrency) || options.concurrency < 1) {
      throw new RangeError("concurrency must be a positive integer");
    }
    this.concurrency = options.concurrency;
  }

  add<T>(id: string, task: Task<T>): void {
    this.records.push({ id, execute: task, state: "queued" });
  }

  snapshot(): TaskSnapshot[] {
    return this.records.map(({ id, state }) => ({ id, state }));
  }

  async run(): Promise<TaskOutcome[]> {
    let cursor = 0;

    const worker = async () => {
      while (true) {
        const record = this.records[cursor];
        if (record === undefined) return;
        cursor += 1;
        record.state = "running";

        try {
          const value = await record.execute();
          record.state = "fulfilled";
          record.outcome = { id: record.id, status: "fulfilled", value };
        } catch (reason) {
          record.state = "rejected";
          record.outcome = { id: record.id, status: "rejected", reason };
        }
      }
    };

    const workers = Array.from(
      { length: this.concurrency },
      () => worker(),
    );
    await Promise.all(workers);

    return this.records.map((record) => {
      if (record.outcome === undefined) {
        throw new Error(`Task ${record.id} finished without an outcome`);
      }
      return record.outcome;
    });
  }
}
```

</details>
